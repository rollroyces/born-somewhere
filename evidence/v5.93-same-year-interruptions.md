# v5.93 — 同一年連續兩次打斷（先決策、再財務）歸零

## 量到的缺陷

v5.61 專門做過「打斷節奏」這件事，當時量到同一生 **0 次同年打斷**。
到 v5.92 重新量 43 條人生，發現回來了：

```
sameYearCollisions: 25   (43 條人生)
```

而且 **25 次全部是同一種組合**：`decision + financeModal`。
分解之後是這樣的組合（各出現次數）：

```
decision + financeModal
  sm_walk            5 次
  de_loan_request    3 次
  de_illness_treat   3 次
  de_care_relative   3 次
  sm_call / de_inflation / de_lottery / sm_pocket / de_parents_care / sm_weekend / sm_volunteer / sm_cook  各 1–2 次
```

財務視窗固定在 25/30/35/40/45/50/55/60 歲彈出（`app.js`），這些年齡同時也可能是
決策年，於是那一年玩家會連續被問兩次。

## 根因：判斷時機比實際開窗早了 100ms

```js
if (STATE.paused) {                       // ← 排程「當下」判斷
  life.financeModalShown.push(age);
  applyInvestmentReturn();
} else {
  life.financeModalShown.push(age);
  setTimeout(() => showFinanceModal(), 100);   // ← 實際開窗在 100ms 之後
}
```

`tryTriggerDecision()` 是用 `setTimeout(..., 120)` 排程的，所以順序是：

```
tick() → 判斷 STATE.paused（false）→ 排程財務(+100ms)
      → 排程 tryTriggerDecision(+120ms) … 但實際上決策 modal 在財務之前就開起來了
```

v5.84 的註解其實已經記錄過這個時序問題（「財務 modal 是 setTimeout(+100ms) 延遲開啟的，
所以同一個 tick 裡 milestoneEvents 跑到這裡時 STATE.paused 還是 false」），
但當時只拿它去修 pause + finance 的疊視窗，**沒有拿它去修同年的連續打斷**。

## 修法

在真正開窗前再看一次，而不是在排程時看：

```js
setTimeout(() => {
  const dm = document.getElementById('decisionModal');
  if (dm && !dm.hasAttribute('hidden')) return;   // 決策已經開著，這年就不再擠玩家
  showFinanceModal();
}, 100);
```

被放棄的那一年本來就已經被寫進 `financeModalShown`，所以不會變成一直跳出來的鬼門關。

## 修之後（同一組 43 條人生、同一個量測腳本）

| | 修之前 | 修之後 |
|---|---|---|
| 同年連續打斷 | **25** | **0** |
| 打斷次數（中位數） | 21 | **20** |
| 打斷次數（平均） | 19.6 | 19.5 |
| 打斷次數（最多） | 25 | 24 |
| 決策事件可達性 | 23 / 24 | **23 / 24** |
| 決策總出現次數 | 408 | **495** |

**決策出現次數反而從 408 增加到 495。** 這是預期之外的收穫：以前財務視窗插在
決策之間時，會消耗掉那一年決策的冷卻期與排程順序；拿掉之後決策平均能多排到一些。
`de_conscription` 仍然從未觸發（設計如此：6/172 國 + 男性 + 18–25）。

## 已知限制

- 被壓掉的財務視窗是真的沒有出現，不是延後。25/30/35/40/45/50/55/60 這些年
  如果同時是決策年，那一年就沒有財務提問。取捨是「一年最多問一次」，
  與 v5.61 訂下的節奏目標一致。
- 這個修法只處理 `decisionModal`。若未來 `focusModal` / `spendModal` 也改成
  延遲開啟，同樣要在 callback 裡補一次檢查。
