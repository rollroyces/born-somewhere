# v6.01 — 訃聞上「刪除所有過去的人生」是個完全不能按的按鈕

## 怎麼找到的

沒有任何症狀報告。是因為做了一件先前沒做過的事：**把每個畫面的每個按鈕都按一遍**，
監聽 `window.onerror`，跳過破壞性操作（刪除／匯出／匯入／聯絡／隱私／條款）。

```
按了 81 個按鈕 → 2 個未捕捉錯誤
  Uncaught ReferenceError: isEn is not defined @5145
  Uncaught ReferenceError: isEn is not defined @5156
```

## 根因：一個從未宣告的變數，四個使用點

`wire()`（第 4945–5241 行，297 行）裡：

```
declarations of isEn inside wire(): NONE
use @ 5145: toast(isEn ? `Showing ${more.length} more` : ...)
use @ 5156: toast(isEn ? 'Life resumed' : '已回到那一生');
use @ 5163: if (confirm(isEn ? 'Delete all past lives?' : '刪除所有過去的人生？')) {
use @ 5166: toast(isEn ? 'All deleted' : '已全部刪除');
```

`isEn` 在這個函式裡**一次都沒有被宣告**。這個檔案其他地方都用
`const isEn = LANG === 'en';` 開頭，但這四個 handler 都假設外層有。

## 四個使用點的實際影響不一樣

| 行 | 按鈕 | 影響 |
|---|---|---|
| 5145 | 「看更多」 | 主動作（追加清單）在前，toast 在後 → 清單會長出來，但**沒有提示**，console 噴錯 |
| 5156 | 「回到那一世」 | `setView` + `startTicker` 在前，toast 在後 → 恢復正常，但**沒有提示** |
| **5163** | **「刪除所有過去的人生」** | **`isEn` 在 `confirm()` 求值之前就拋出 → 整顆按鈕完全沒反應** |
| 5166 | 同上，被 5163 擋住 | 不可達 |

第 5163 這顆是最嚴重的：使用者按下去，**沒有確認對話框、沒有刪除、沒有任何提示**，
只有 console 一行錯誤。這是訃聞畫面上的主要操作之一。

## 修法

四處全部改成本專案 toast 一貫的寫法（`downloadLifeCertPNG()` 等處都是這樣）：

```js
toast(LANG==='en' ? 'Life resumed' : '已回到那一生');
if (confirm(LANG==='en' ? 'Delete all past lives?' : '刪除所有過去的人生？')) {
```

用 `LANG==='en'` 而不是補一個 `const isEn = LANG === 'en';`，是因為
`wire()` 只在初始化時跑一次，而 `isEn` 這種常數在那個時機取值的話，
之後玩家切換語言就會停在舊語言。寫在事件處理器裡每次都重新讀 `LANG` 才正確。

> 順帶一提：這四處其實有**兩組重複的 handler**。第 3860 行
> （`showManageRecordsModal` 裡的「全部刪除」）本來就寫對了，
> 第 5163 行（`wire()` 裡的訃聞按鈕）是另一份漏改的副本。
> 第一次修只替換到第一個比對結果，後來改用行號定位才補齊。

## 修之後（三筆過去紀錄）

| | 修之前 | 修之後 |
|---|---|---|
| 「看更多」 | 清單有長，無提示，console 報錯 | 清單有長 ✅ 提示「顯示 0 段過去」✅ |
| 「回到那一世」 | 恢復成功，無提示，console 報錯 | 恢復成功 ✅ 提示「已回到那一生」✅ |
| 「刪除所有」 | **完全無反應** | 確認框「刪除所有過去的人生？」✅ 3 筆 → 0 筆 ✅ 提示「已全部刪除」✅ |
| 未捕捉錯誤 | 2 個 | **0 個** |

（「顯示 0 段過去」是正確行為：`endShowMore9` 取 `past.slice(5, 14)`，
只有 3 筆紀錄時本來就沒有第 6～14 筆。）

## 這個 bug 為什麼能活這麼久

它是**只有在按下去那一刻才會拋**的錯誤，而且：

- 5163 那顆拋在 `confirm()` 之前，所以連對話框都沒出現 —— 從畫面上看
  就是「按了沒反應」，非常容易被當成「這個按鈕就是還沒做」而略過
- 另外兩顆的主動作都在拋錯之前完成，功能其實正常，只是少了 toast

要靠讀程式碼很難注意到（`isEn` 是一個到處都在用的合理變數名），
必須實際執行到那幾個按鈕才會暴露。

## 建議（這次沒做）

這個 bug 屬於「未宣告識別字」，是靜態檢查的工具（linter / `tsc --noEmit`）
最擅長抓的類型。這個專案目前沒有 package.json，也沒有任何 lint 設定。
加一套 ESLint（或至少開啟 `no-undef`）可以一次掃出全檔案同類問題，
成本很低 —— 但那屬於引入工具鏈，是一次範圍決策，這裡只提出建議不擅自執行。
