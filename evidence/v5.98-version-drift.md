# v5.98 — 五份版本字串，全部漂移；分享圖上寫的是 v5.12 和 v5.2

## 量到的缺陷

匯出「分享出生卡」之後，把 SVG 內容讀出來，頁尾是：

```
出生登記 · born-somewhere v5.12 · 真實統計
```

當時線上跑的是 **v5.97**。

再查「生命證書」，頁尾是：

```
生命證書 · born-somewhere v5.2 · 真實統計
```

## 完整的漂移地圖

| 位置 | 內容 | 當時應為 | 誰看得到 |
|---|---|---|---|
| `index.html:583` | `v5.97` | v5.97 ✅ | 頁尾 |
| `sw.js:5-6` | `born-somewhere-v5.97` / `5.97.0` | v5.97 ✅ | 內部 |
| `app.js` `APP_VERSION` | **`5.19.0`** | v5.97 ❌ | **更新說明標題、意見回報內容** |
| 分享出生卡頁尾 | **`v5.12`** | v5.97 ❌ | **匯出的圖（會被別人看到）** |
| 生命證書頁尾 | **`v5.2`** | v5.97 ❌ | **匯出的圖（會被別人看到）** |

五份各自硬編碼，沒有任何機制保證它們一致。`APP_VERSION` 停在 5.19.0
是因為它 v5.19 寫下之後就沒再被維護過 —— 之後每次上線只會動 `index.html`
和 `sw.js`（因為那是 deploy 儀式的一部分），另外三份就留在原地。

分享圖特別不能錯：那是玩家要貼給別人看的東西，上面印著錯誤的版本號
會讓人覺得這是個沒在維護的專案。

## 修法

### 1. 單一來源

把 `APP_VERSION` / `APP_BUILD` 移到檔案最上方（原本在第 5510 行，
遠晚於所有使用點），並更新為正確值：

```js
const APP_VERSION = '5.98.0';
const APP_BUILD  = '2026-10-23';
```

### 2. 兩張匯出圖改讀同一份

```js
// 生命證書頁尾
${...} · born-somewhere v${APP_VERSION} · ...

// 出生卡頁尾
${isEn ? 'Birth certificate · born-somewhere v'+APP_VERSION
       : '出生登記 · born-somewhere v'+APP_VERSION} · ...
```

### 3. `i18n_audit.py` 加第 6 項檢查，擋住以後再漂

因為這個專案只有這一個稽核腳本，版本一致性檢查放進去最省事：

- `index.html` 的 footer 版號、`app.js` 的 `APP_VERSION`、`sw.js` 的 `CACHE_NAME`
  三者必須一致
- 含「真實統計 / Real statistics」的行裡不得再出現硬編碼版本

寫的時候踩到一個誤判並修掉：規則一開始掃全文，
把檔頭註解裡的 `/* born-somewhere v2 */` 判成違規。但那是
`STORAGE_KEY = 'born-somewhere-v2'` 的**資料格式版本**，跟 app 版本是兩套編號。
規則收斂成只檢查兩張匯出圖的頁尾那幾行。

負向測試（把 footer 改成 v5.99）：

```
VERSION  app.js APP_VERSION.  [!= index.html v5.99]  '5.98.0'
VERSION  sw.js CACHE_NAME.   [!= index.html v5.99]  '5.98'
TOTAL: 2
exit code on drift = 1
exit code when clean = 0
```

## 已知限制（這次**沒有**修）

**更新說明的內容停在 v5.19。** 標題現在正確顯示 v5.98.0，但 `CHANGELOG` 陣列
最新的條目是 v5.19，也就是說 v5.20～v5.98 這段的所有修正**在更新說明裡看不到**。

沒有補的原因是：要補就得為每個版本寫條目，而且每個條目在 `data/i18n.json`
裡要有 9 種語言的 key。這是內容撰寫，不是修 bug，而且把 78 個版本逐條列出
對玩家也沒什麼價值。比較合理的做法是改成「近期重要修正」的精選列表
（例如本專案紀錄的十來個關鍵修正），但那是一次內容決策，值得先問過再動。

目前玩家仍可從頁尾看到當前版本號，`CHANGELOG.md` 也在 repo 裡。
