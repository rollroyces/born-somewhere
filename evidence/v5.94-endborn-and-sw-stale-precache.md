# v5.94 — 訃聞上的「2024/女 生」，以及 Service Worker 把舊檔鎖進新版本

兩個獨立缺陷，在同一輪裡被同一個現象牽出來。

## 缺陷一：`event.born_in2` 是一句從句，被當成標籤用

訃聞的身分證明列（`index.html:392` → `app.js:3569`）：

```js
$('#endBorn').textContent = life.year + '/' + t('event.born_in2', sexLabel);
```

但這個 key 的九個翻譯全都是**一句話**：

| 語言 | 值 | 實際畫出來 |
|---|---|---|
| zh-Hant / zh-Hans | `"{} 生"` | `2024/女 生` |
| en | `"Born {}"` | `2024/Born M` |
| ko | `"{}출생"` | `2024/여출생` |
| ja | `"{}生まれ"` | `2024/男生まれ` |
| vi | `"Sinh {}"` | `2024/Sinh Nữ` |
| fr | `"Né {}"` | `2024/Né F` |
| th | `"เกิด {}"` | `2024/เกิด F` |
| es | `"Nacido {}"` | `2024/Nacido M` |

**九個語言全部壞掉。** 繁中還多一個空格（「女 生」）。

`grep` 確認這個 key 全站只有這一個使用點，所以不是共用字串被誤用，
而是這個 key 從一開始就是照「出生事件敘述句」寫的，卻被用在「出生年／性別」欄位。

修法：九個值都改成 `"{}"`，欄位變成乾淨的 `2024/女`。
（同層的 `log.born_in` = `在 {} 出生` / `Born in {}` 用在出生事件敘述裡，是正確的，沒動。）

修後實測：

| | 修之前 | 修之後 |
|---|---|---|
| zh-Hant | `2024/女 生` | `2024/女` |
| en | `2024/Born M` | `2024/M` |
| ko | `2024/여출생` | `2024/남` |
| ja | `2024/男生まれ` | `2024/男` |

## 缺陷二（比較嚴重）：Service Worker 預存舊檔，而且沒有任何錯誤

修完缺陷一後重載，畫面**還是舊的**。直接比對 cache 與 network：

```
cache  born-somewhere-v5.93 → data/i18n.json:  "event.born_in2": "{} 生"   ← 舊
network                             /data/i18n.json:  "event.born_in2": "{}"    ← 新
```

剛剛升級的 `CACHE_NAME` 裡，裝的是**舊內容**。根因在 `sw.js`：

```js
// 舊碼
cache.add(url)                       // 走瀏覽器預設 HTTP cache
fetch(req).then(...)                 // 同樣走 HTTP cache
```

`cache.add()` 與背景重新驗證都用預設的 HTTP cache mode，於是磁碟上的舊副本
被拿來填進「全新的」cache。**版本號升了、CACHE_NAME 升了、footer 顯示新版本，
但玩家拿到的是舊檔，而且 console 一個字都沒有。**

這對這個專案特別危險：每次上線都靠「`index.html` 版本號 + `CACHE_NAME` 升版」來
確保使用者拿到新內容。一旦預存會撈到 HTTP cache 舊檔，那套機制就形同虛設。

修法兩處都要繞過 HTTP cache：

```js
// install：強制 reload
cache.add(new Request(url, { cache: 'reload' }))

// fetch：背景重新驗證也強制 reload
fetch(new Request(req, { cache: 'reload' })).then(...)
```

修完重測：新的 `born-somewhere-v5.94` cache 裡 `data/i18n.json` 是
`"event.born_in2": "{}"`（正確的新值），`app.js` 裡也確認含 v5.89 之後的程式碼。

## 附帶說明

這次量測中我踩到一次自己的陷阱：**清掉 SW 與 caches 之後重載，仍讀到舊值**。
原因正是上面這個缺陷 —— 清 cache 不會清 HTTP disk cache，所以清完重載，
新的 SW 又從 HTTP cache 撈舊檔回來。修好之後同樣的清除流程才真的有效。
以後驗證前線版本時，這點要一併算進去。

## 驗證方式

```js
// 直接比對 cache 與 network，而不是只看畫面
const c = await caches.open((await caches.keys())[0]);
const hit = (await c.keys()).find(k => k.url.includes('i18n.json'));
const cached = await (await c.match(hit)).text();
const live = await fetch('/data/i18n.json?bust=' + Date.now()).then(r => r.text());
// cached 必須包含新值
```

### 已知限制

- `sw.js` 自己不在 `APP_SHELL` 清單裡（瀏覽器不建議快取 SW 腳本本身），
  所以沒有驗證「舊 SW 會不會拿到新 sw.js」。實際更新路徑是標準的
  `skipWaiting()` + `clients.claim()`，這段沒有改動。
- 背景重新驗證改成 `cache:'reload'` 之後，每次命中都會打一次網路。
  對這個規模的靜態站沒有問題，但如果之後檔案變多，應該改成節流或用
  `stale-while-revalidate` 的時間窗，而不是每個請求都重抓。
